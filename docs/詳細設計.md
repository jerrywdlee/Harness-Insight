## 0. エグゼクティブサマリ

**Harness-Insight** は、開発者が AI コーディング・アシスタント（GitHub Copilot Chat / Cursor / Claude Code / OpenAI Codex CLI / OpenClaw / HermesAgent / Antigravity）を使ったセッションを **後付けで**「自己評価 ＝＞ 自己改善」のループに乗せる **汎用 SKILL** である。

特徴は以下の 5 点：

| # | 特徴 | 価値 |
|---|---|---|
| 1 | **7 種の AI ハーネスを単一スキーマに正規化** | ハーネス横断のメタ分析が可能 |
| 2 | **多言語フォールバック (JS → Python → AI 自力)** | 実行環境を選ばない |
| 3 | **コンテキスト分離（context: fork）** | メイン対話のトークンを汚染しない |
| 4 | **3 段階反映（none / project / global）** | ユーザーが反映粒度を完全制御 |
| 5 | **SKILL 自身がドッグフード対象** | 自リポジトリの開発履歴で自分を改善できる |

配布形態:
```bash
npx skills add jerrywdlee/Harness-Insight   # skills CLI 経由
npx harness-insight              # 直接インストーラ
```

## 1. 設計の動機（Why）

### 1.1 解決したい問題
AI コーディングを 1 セッション使った後、「うまく使えたか／ハルシネーションを発生させたか／手戻りが多かったか」を **その場で振り返る仕組み** が、どのハーネスにも標準で存在しない。
振り返れないので **次回も同じミスを繰り返す**（同じ強制停止、同じ手動コーディング、同じ曖昧プロンプト）。

### 1.2 既存ソリューションとの差
| 既存手段 | 限界 |
|---|---|
| LangSmith / Langfuse 等の trace SaaS | アプリ側に instrument が必要、Vibe coding ハーネスは未対応 |
| ハーネス独自の telemetry | ハーネス間で分析不可、ベンダー側のみが見える |
| 手動レトロスペクティブ | 主観的、形式知化されず継承不可 |

### 1.3 アプローチ
1. ハーネス各自が **既に書き出している生ログ** を読む（追加 instrument 不要）。
2. **共通スキーマに正規化**してハーネス差を吸収。
3. **メタ分析を別コンテキストで実行**（メイン対話を汚さない）。
4. 改善ルールを `AGENTS.md` 系ファイルにマーカー付きで埋め込み、**次回セッションが必ず読む** 場所に置く。

## 3. 共通スキーマ（Normalized JSONL）

`.harness_insights/normalized.jsonl` は 1 行 1 イベント。**SKILL 全体で唯一のハブ・データ構造**。

```json
{
  "ts": "2026-04-29T10:15:32.120Z",
  "actor": "user | ai | system",
  "action_type": "prompt | ai_response | code_edit | tool_call | interrupt | error | system",
  "content": "発話本文 or diff (unified format)",
  "meta": {
    "tokens_in": 0,
    "tokens_out": 0,
    "files": ["src/foo.ts"],
    "tool": "edit_file",
    "duration_ms": 0,
    "source": "copilot.transcript"
  }
}
```

### 3.1 設計判断
- **JSONL** 採用理由: ストリーミング処理可能・追記容易・各行独立で破損耐性が高い。
- **`action_type` を 7 値に固定**: ハーネス差を吸収しつつ、定量分析の集計軸を一定にする。
  - `code_edit` には「AI が編集系ツールを呼んだ」「ユーザーがエディタで直接編集した」の両方を含める（差は `actor` で区別）。
- **`meta.files`**: rework 検出のキー。同一ファイルの再編集回数を集計する。
- **`meta.source`**: `copilot.transcript` / `copilot.debug` のように **アダプタ側で経路を明示** することで、後段の LLM 解析が信頼度を判定可能にする。

## 4. Step 1: DETECT — ハーネス検知

### 4.1 検知優先順位と保存先

| 優先 | Harness | 検知パス（実装ベース） |
|---|---|---|
| 1 | GitHub Copilot Chat | **`%APPDATA%/Code/User/workspaceStorage/*/GitHub.copilot-chat/transcripts/*.jsonl`**（実対話履歴・優先）<br>`.../GitHub.copilot-chat/debug-logs/*`（telemetry・フォールバック） |
| 2 | Cursor | `%APPDATA%/Cursor/logs/**`, `~/.cursor/sessions/*.jsonl` |
| 3 | Claude Code | `~/.claude/projects/<encoded-cwd>/*.jsonl` |
| 4 | OpenAI Codex CLI | `~/.codex/sessions/*.jsonl`, `~/.codex/history/*.jsonl` |
| 5 | OpenClaw | `./.openclaw/sessions/*.jsonl` |
| 6 | HermesAgent | `./.hermes/runs/*/overview.txt` |
| 7 | Antigravity | `./.antigravity/transcripts/*.jsonl` |
| 99 | Unknown | 対話で保存先を問い合わせ |

### 4.2 Copilot 検知の二段構え（v0.2 で発見・v0.3 で修正済）
v0.1 では `debug-logs/main.jsonl` のみを見ていたが、これは **telemetry イベント中心** で `prompts / edits / interrupts` がほぼ 0 件しか取れない欠陥があった。
v0.3 でアダプタを書き換え、**`transcripts/<sessionId>.jsonl`** を優先採用するよう変更。同ファイルには `user.message` / `assistant.message` / `tool.execution_start` 等の **対話イベント** が直接記録されている。

検知関数の擬似コード:
```js
function detectCopilot(base) {
  const transcripts = walk(base, /transcripts\/.*\.jsonl$/);
  const debugLogs   = walk(base, /debug-logs\/.*\.(jsonl|log|json)$/);
  return transcripts.length ? transcripts : debugLogs;  // 優先
}
```

検証結果（同セッション）:
| 経路 | events | prompts | edits |
|---|---|---|---|
| debug-logs (旧) | 1824 | 0 | 0 |
| **transcripts (新)** | **330** | **17** | **71** |

## 5. Step 2: EXTRACT — 多言語フォールバック

### 5.1 フォールバック・チェーン（必須順序）

| 順 | 条件 | 実行 |
|---|---|---|
| 1 | `node -v` 成功 | `node scripts/extract.js` |
| 2 | `python --version` 成功 | `python scripts/extract.py` |
| 3 | 両方不可 | 実行中の AI Agent が [`templates/manual_extract_prompt.md`](templates/manual_extract_prompt.md) に従い **自力で** 抽出 |

### 5.2 アダプタ実装ポリシー
- 各ハーネスの生ログ → 共通スキーマへの変換は **`scripts/adapters/<harness>.{js,py}` に分離**。
- すべて **読み取り専用**（生ログを書き換えない）。
- JS と Python で **同じ harness 名 → 同じ出力** を保証（バリデーションは目視 + 行数比較）。

### 5.3 サブコマンド・オプション
| オプション | 効果 |
|---|---|
| `--list` | 検知セッション一覧のみ表示（抽出しない） |
| `--session <substring>` | パスに該当部分文字列を含むセッションだけ抽出 |
| `--out <path>` | 出力先ファイルを変更 |
| `--append` | `--out` と併用して追記（複数セッション統合） |

これらは「**新トリガーを増やすより既存サブコマンドで賄う**」設計判断（後述 §11 Lesson 2）の結果である。

### 5.4 .gitignore 自動追記
JS/Python/Agent 自力モードのいずれでも `/.harness_insights/` 行を `.gitignore` に必ず追記する。
v0.3 で「**`.gitignore` が非 UTF-8 の場合に Python 抽出が落ちるバグ**」を修正（`errors="ignore"` 化）。

## 6. Step 3: ANALYZE — 定量 ＋ 定性

### 6.1 環境チェック順序
```
1. node -v            → scripts/analyze.js
2. python --version   → scripts/analyze.py
3. pwsh / powershell  → scripts/analyze.ps1
4. すべて失敗         → LLM フォールバック (Few-shot, templates/fallback_prompt.md)
```

### 6.2 定量指標と計算式

| 指標 | 計算方法 | 重み |
|---|---|---|
| `delegation_score` | (AI への委任 actions / 全 actions) × 100 | 30% |
| `prompt_clarity` | プロンプト長・制約語密度のヒューリスティクス | 20% |
| `manual_coding_time_min` | `ai_response → 次 prompt` 間の連続 user `code_edit` 合計分（5 分以上を opportunity loss と判定） | 20% |
| `interrupt_count` | `action_type == "interrupt"` の総数 | 15% |
| `rework_ratio` | 同一ファイル再編集回数 / 総編集回数 | 15% |

**総合スコア**:
```
total = max(0, 100 − opportunity_loss×3 − interrupt_count×4 − max(0, rework_ratio−30)×0.5)
```

### 6.3 `breakdown` フィールド（v0.2 で追加）
v0.1 ではユーザーから「採点の詳細が出されていない」報告があり、`metrics.json` に **`breakdown` を必須化**：

```json
"breakdown": {
  "delegation_contrib":  21.6,
  "clarity_contrib":     12.8,
  "opportunity_penalty": -3,
  "interrupt_penalty":   -12,
  "rework_penalty":      -2.5,
  "formula": "100 - opportunity_loss_count×3 - interrupt_count×4 - max(0, rework_ratio-30)×0.5"
}
```

3 言語パーサー（JS / Python / PowerShell）すべてが同フィールドを出力する。
レポート (Step 4) はこの構造をそのまま採点表として表示する義務を負う（「省略禁止」を SKILL.md に明記）。

### 6.4 定性分析（LLM 担当・別コンテキスト）
別コンテキスト (`context: fork`) で以下を判定：
- ハルシネーションの主因
- 強制停止の直前のプロンプトの不足制約
- 手戻りパターン（ライブラリ誤用 / 出力フォーマット違い / ドメイン誤解）

### 6.5 トレンド分析
`.harness_insights/history.jsonl` に過去スコアを追記、前回比 / 改善トラック を表示。

### 6.6 LLM フォールバック・スコア
パーサー実行不可時は [`templates/fallback_prompt.md`](templates/fallback_prompt.md) で LLM が `metrics.json` を直接生成。同ファイルにも **`breakdown` を必須出力** として明記。

## 7. Step 4: REPORT — 二元化レポート

### 7.1 Human-facing（必須フォーマット）

```markdown
## 🪞 Self-Reflection Report

**総合 AI 委任度スコア:** 84 / 100  （前回 比較: +5 / -2 / N/A）

### 📊 採点内訳（省略禁止）

| 指標 | 実測値 | 重み | 寄与/減点 | コメント |
|---|---|---|---|---|
| delegation_score      | 90/100 | 30% | +27.0 | … |
| prompt_clarity        | 80/100 | 20% | +16.0 | … |
| manual_coding_time_min| 0 min  | 20% | -0    | … |
| interrupt_count       | 1      | 15% | -4    | … |
| rework_ratio          | 24%    | 15% | -0    | … |
| **total_score**       | **84** | —   | …     | |

### あなたへのコーチング
…（最大 3 件）

### 良かった点
…（1〜2 件）
```

### 7.2 System-facing
`.harness_insights/proposed_rules.md` に保存：
```markdown
## Proposed Rule (auto-generated YYYY-MM-DD)
- Trigger: <根拠ログ事象>
- Rule:    <次回 AI が守るべき行動>
- Apply to: AGENTS.md
- Evidence: <ログ抜粋>
```

### 7.3 設計判断（Lesson 1）
レポート仕様（特に採点内訳テーブル）は **コードより先にサンプルとして固定** すべきだった。v0.1 では実装先行で抜け漏れが発生し、別 PC 上で初めて発覚した。
**v0.2 以降の SKILL 開発ルール**: 出力サンプル（人間可読 + JSON 構造）を SKILL.md / templates/ の両方に先に固定 → 実装着手。

## 8. Step 5: APPLY — 3 段階反映

### 8.1 ユーザーへの選択提示

| 値 | スコープ | 反映先（優先順） |
|---|---|---|
| `1` / `none` | 反映しない | （`proposed_rules.md` のみ残す） |
| `2` / `project` ★既定 | プロジェクト | ① `./AGENTS.md` ② `./.github/copilot-instructions.md` ③ `./.cursor/rules/harness-insight.md` |
| `3` / `global` | グローバル | ① `~/.agents/AGENTS.md` ② `%APPDATA%/Code/User/prompts/harness-insight.instructions.md` ③ `~/.cursor/rules/harness-insight.md` |

無入力 / Enter のみは **2 (project)** として扱う。

### 8.2 マーカー方式

追記は必ず以下マーカーで囲む。後続セッションが **同マーカーブロックを置換** することで重複追記を防ぐ:

```markdown
<!-- harness-insight: 2026-04-29 scope=project -->
…rule body…
<!-- /harness-insight -->
```

### 8.3 設計判断
- 「無条件に AGENTS.md に書き込む」設計は危険（プロジェクト固有設定を全 PJ に伝播させてしまう）。
- 「project / global」を **明示的に分ける** ことで、汎用ルールと PJ 固有ルールを分離可能。
- `none` を残すのは「**ルール自動生成は欲しいが反映タイミングは別途決めたい**」というニーズ対応。

## 9. SKILL 起動トリガー

| トリガー | 動作 | 用途 |
|---|---|---|
| **`/harness-insight`** ★推奨 | Step 1〜5 を全実行 | 通常の振り返り |

## 10. 安全性・運用ポリシー

| 観点 | 設計 |
|---|---|
| メイン対話の汚染 | Step 3-4 は **必ず別コンテキスト (`context: fork`)** で実行 |
| 生ログの保護 | アダプタは **読み取り専用**、改変禁止 |
| 機微情報 | LLM 解析プロンプトに「個人名 / トークン現出時はマスク」を明記 |
| ファイル汚染 | `.harness_insights/` は `.gitignore` 自動追記、配布物には **非含有** |
| ユーザー承認 | Step 5 は必ず 3 択を提示、無断書換禁止 |

## 11. 開発ヒストリーから得た Lesson（ドッグフード成果）

本 SKILL は **自リポジトリのセッションで自分自身を分析** し、得られた `proposed_rules.md` を `AGENTS.md` に反映するというドッグフード運用を行っている。

### Lesson 1: 出力サンプルを実装より先に固定する
- **トリガー**: 別 PC の Antigravity で「採点の詳細が出されていない」報告。
- **学び**: SKILL/レポート系機能の新設時は、**出力サンプル（人間可読 + JSON 構造）を SKILL.md / templates/ の両方に先に固定** してから実装する。
- **対応**: v0.2 で `breakdown` を 3 言語パーサー + 2 LLM プロンプトに横断追加。

### Lesson 2: 既存サブコマンドで賄えないか 1 ターン確認する
- **トリガー**: `/extract-logs` 独立トリガーを追加直後、ユーザーが「サブコマンド機能を知らなかった、不要」と取消。
- **学び**: 既存仕様に **新トリガー / 新サブコマンド** を増やす要望が来たら、まず「既存の `/<trigger> <sub>` で代用可能か？」を 1 ターン確認する。
- **対応**: v0.2 で `/extract-logs` 関連の 5 ファイル横断変更を全 undo。

### Lesson 3: ハーネスの保存先は二重化されている
- **トリガー**: copilot adapter が `debug-logs/main.jsonl` の telemetry のみを拾い、prompts / edits が 0 件のままだった（2 セッション連続）。
- **学び**: ハーネスは **「telemetry / debug」と「実対話 transcripts」が別ディレクトリ** に保存されることがある。アダプタは両方を見て、対話イベントを含む方を優先するべき。
- **対応**: v0.3 で `transcripts/*.jsonl` を優先検知、`tool.execution_start` の `toolName` を編集系（`code_edit`）／非編集系（`tool_call`）に分類。

### Lesson 4: ファイル横断更新ルール（4 箇所同時更新）
新ハーネス追加時は **必ず 4 箇所を同時更新**：
1. `scripts/adapters/<harness>.{js,py}`
2. `scripts/extract.js / extract.py` の `detectHarness()` / `detect_harness()`
3. `SKILL.md` の DETECT 表とファイル構成
4. `skill.json#files[]` と `README.md` の対応ハーネス行

これを `AGENTS.md` のドッグフード規約として明記し、AI が自動で漏らさないようガード。

## 14. 既知の制約と将来計画

### 14.1 既知の制約
- Cursor / Claude Code / Codex CLI のアダプタは **保存先パスのみ** 検証済で、実セッション流入での動作確認はユーザー報告ベース。
- LLM フォールバック時の `breakdown` は推計値（`evidence[]` で根拠ログ ID を併記する設計だが、精度はモデル依存）。
- `prompt_clarity` のヒューリスティクスは英 / 日の制約語のみ対応（多言語対応は v1.x の課題）。

### 14.2 将来計画
- ハーネス追加: Continue / Aider / OpenDevin 等。
- ダッシュボード: `history.jsonl` を可視化する `harness-insight serve` の追加検討。

## 15. ブログ記事執筆向けポイント

ブログ作成 LLM が引き出してほしいストーリー軸：

1. **「Vibe coding を計測可能にする」 という切り口**
   - 「速さの錯覚」と「実際の AI 委任度」のギャップを定量で示す（rework_ratio や opportunity_loss）。
2. **マルチハーネス対応の難しさ**
   - 同じ「対話履歴」でも保存場所・スキーマがハーネスごとに違う。共通スキーマ設計と adapter 分離の意義。
3. **AI が AI を評価するパラドックスへの解答**
   - メイン対話を汚さない `context: fork`、生ログ読み取り専用、3 段階反映スコープ。
4. **ドッグフード駆動の SKILL 改善**
   - v0.1 のレポート不備 → v0.2 で `breakdown` 追加 → v0.3 で transcripts adapter 修正。
   - 自分の SKILL を自分のセッションで分析することで欠陥が連鎖的に発見された実例。
5. **ユーザー主権の設計**
   - 反映スコープ 3 段階 / マーカー方式の置換 / 配布物からのドキュメント除外などの「**自動だが上書きしない**」原則。
6. **学んだ Lesson の汎用性**
   - 出力サンプル先行・既存機能で代用可能か確認・保存先二重化の発見は **SKILL 開発全般に適用可能**。
